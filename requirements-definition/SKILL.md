# 要件定義書作成スキル

ユーザーとの対話を通じて曖昧なアイデアを実装可能な要件定義書に仕上げるスキル。

出力形式（MD / HTML / 両方）の最終決定は **artifact-format skill に委譲する**。本スキルはヒアリングと内容生成に責任を持ち、形式判定はartifact-formatに任せる構成。

## ワークフロー

### 1. ヒアリング開始

ユーザーの最初の入力から、プロジェクトの概略を把握する。構成要素（UI / API / バッチ / 業務自動化等）を特定する。複合構成（例: Web UI + API + バッチ）が一般的なので、複数選択を前提とする。

### 2. 段階的ヒアリング

[questioning-guide.md](references/questioning-guide.md)を参照し、以下の順序で質問を進める:

1. **プロジェクト概要・背景・目的** — なぜ作るのか、構成要素は何か
2. **ターゲットユーザー・利用主体** — 誰が（何が）どう使うのか
3. **機能棚卸しと優先度付け** — 全体像を把握し、Must/Should/Couldに分類
4. **Must機能の詳細深掘り** — I/O、バリデーション、エラー、インターフェース要件
5. **非機能要件** — 性能、セキュリティ、可用性、運用
6. **技術要件** — 技術スタック（未定でも可）

#### ヒアリングのルール

- 一度に出す質問は必要な数だけ。多すぎない。
- 曖昧な回答は具体化するまで掘り下げる（「適切に」→具体的な条件に）。
- ユーザーの回答から推測できることは確認を取りつつ補完する。
- **まず全機能を洗い出し、優先度を付けてからMust機能の詳細に入る。**
- Should/Could機能は概要レベルの記載に留め、詳細深掘りはMust機能に集中する。
- 機能の詳細深掘りでは、構成要素に応じた確認項目を使い分ける:
  - UI → 画面要件（レイアウト、遷移、インタラクション）
  - API → エンドポイント、リクエスト/レスポンス、認証、レート制限
  - バッチ → 実行トリガー、入出力ソース、リトライ、冪等性
  - 業務自動化 → 対象システム、操作手順、前提条件、失敗時の再開方法、人間の介入ポイント
- 「他にありますか？」で漏れを防ぐ。
- 「〜の場合は？」でエッジケースを洗い出す。

### 3. ヒアリング完了判断

以下をすべて満たしたらヒアリング完了:
- プロジェクトの目的・背景・構成要素が明確
- ターゲット（ユーザー / 外部システム / スケジューラ等）と主要な利用シーンが特定済み
- 機能の全体像と優先度が整理済み
- Must機能について以下が定義可能なレベル:
  - 共通: I/O・バリデーション・エラーハンドリング・データ永続化
  - UIを含む機能: 画面要件（レイアウト、遷移、インタラクション）
  - APIを含む機能: エンドポイント、認証、レート制限
  - バッチを含む機能: 実行トリガー、リトライ、冪等性
  - 業務自動化を含む機能: 対象システム、操作手順、前提条件、失敗時の再開方法、人間の介入ポイント
- 非機能要件が構成要素に応じて確認済み（性能・セキュリティ・可用性・運用）
- 技術スタックは確認済み（未定でも可）

完了時は「ヒアリング内容をもとに要件定義書を作成します。よろしいですか？」と確認する。

ユーザーが途中で「もういい」「これで作って」と言った場合は、得られた情報の範囲で要件定義書を作成し、未確定事項は「未確定事項一覧」セクションにまとめる。

### 4. 出力形式の判定（artifact-format に委譲）

要件定義書の生成に入る前に、**artifact-format skill** を参照して出力形式を判定する。

#### このスキルにおける典型的な判定

要件定義書のコンテキストでは、以下のパターンが多い:

| 状況 | 判定 | 理由 |
|---|---|---|
| 通常の実装向け要件定義（チーム内、エンジニアのみ） | **MDのみ** | 実装入力・git管理・継続更新 |
| 複雑な状態遷移・データフロー・システム間連携を含む | **MD + HTML** | MD=正本、HTML=構造可視化（Mermaidで足りない場合） |
| 経営層・PM・非エンジニアにも共有する要件定義 | **MD + HTML** | MD=エンジニア向け正本、HTML=非エンジニア向け視覚サマリー |
| 複数案を比較して合意形成したい探索フェーズ | **HTMLのみ** または MD+HTML | 並列比較に視覚要素が必須 |

#### 判定の進め方

1. **デフォルトは「MDのみ」**: 通常の実装向け要件定義はMDで足りる。Mermaidで画面遷移図やシーケンス図を埋め込めば、ほとんどのケースは視覚補助HTMLが不要。
2. **ヒアリング中に以下のシグナルを拾ったら HTML 併用を検討**:
   - 「経営層にも見せる」「PMが読む」「非エンジニアにレビューしてもらう」 → ステークホルダー共有あり
   - システム構成が複雑（5サービス以上連携・複数バッチの依存関係・状態が10以上）→ Mermaidでは追いきれない
   - 「動くデモ」「クリックできるモック」「触って確認したい」 → 編集UI/プロトタイプ系（HTMLのみ寄り、ただしspecとしては別途MDが要る）
3. **判断が割れた時のみ1問確認**: 「この要件定義書はエンジニア向けのみですか？それとも非エンジニアにも共有しますか？」

#### artifact-format に従う

詳細な判定アルゴリズム・最低品質ライン・アンチパターンは artifact-format skill 本体を参照する。本スキル内では再掲しない（重複管理を避ける）。

### 5. 要件定義書の生成

判定された形式に応じて出力する。

#### MDのみ の場合

[document-template.md](references/document-template.md)のテンプレートに沿って要件定義書を生成する。プロジェクトの構成要素に応じて該当するセクションのみ含める。

生成ルール:
- ヒアリングで得た情報を正確に反映する。
- 要求仕様にはID・受け入れ条件を含める。人間ユーザー向けはユーザーストーリー形式、システム連携・バッチ・業務自動化はシステム要求形式を使う。
- 機能要件はI/O表・バリデーション表・エラーハンドリング表を統一的に表形式で記載する。
- 画面遷移図はMermaidで記述する（UIを含む場合のみ）。
- 推測で補完した箇所や未確定の項目は「未確定事項一覧」セクションに集約する（本文中に散在させない）。
- 技術スタックは選定理由を含める（未定の場合は「未定」と明記）。
- 構成要素に存在しないセクションは出力しない（例: UIがなければ画面構成セクションを丸ごと省略）。

#### MD + HTML の場合

MDは上記ルールで生成する（正本）。

HTMLは**視覚補助に徹する**:
- MDの本文をコピーしない。図・色・インタラクションだけを担当する
- 含めると効果的な視覚要素:
  - **システム構成図**（コンポーネント間の関係をSVGで）
  - **データフロー図**（リクエスト→処理→レスポンスの流れ）
  - **状態遷移図**（複雑な業務フロー・ワークフロー）
  - **影響範囲マップ**（機能変更が触るシステム範囲）
  - **非エンジニア向けサマリー**（経営層共有時のみ・色で機能優先度を可視化）
- HTML冒頭に `正本: ./xxx.md` のリンクを必ず明記
- `frontend-design` skill を必ず参照してから生成する（generic AI HTMLを避ける）
- ファイル名はMDと揃える: `requirements.md` + `requirements.html`

詳細は artifact-format skill の「出力時の注意 > HTMLを選んだ場合」を参照。

### 6. レビューと修正

生成後、ユーザーにレビューを依頼する。指摘があれば修正し、要件定義書を更新する。

MD+HTMLの両方を作った場合、**MDが更新されたらHTMLは捨てて再生成する**（差分同期しようとしない。artifact-formatの規律に従う）。
